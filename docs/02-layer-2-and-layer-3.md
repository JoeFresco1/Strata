# Layer 2 And Layer 3

Layer 2 and Layer 3 should behave as controlled descents from the selected and approved items above them.

## Layer 2

- Expand only the pillars the user kept or prioritized.
- Generate subfeatures that are specific but still below the pillar level.
- Include common, edge-case, admin, reporting, automation, integration, and data-related subfeatures when relevant.
- Use the same compression and saturation logic as Layer 1, but scoped to the parent pillar.
- Preserve rejected ideas so the model does not regenerate them later.

## Layer 3

- Expand selected subfeatures into implementation-ready specs.
- Produce structured JSON with user stories, inputs, outputs, edge cases, UX screens, data requirements, acceptance criteria, risks, and implementation notes.
- Keep the spec tied to the parent pillar and subfeature.

## Review behavior

- The user should be able to review Layer 2 and Layer 3 items with the same keep/cut/rename/prioritize workflow.
- Spec items should remain exportable even if the user later edits or renames their parent items.
