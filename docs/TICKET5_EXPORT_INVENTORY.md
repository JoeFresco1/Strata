Status: pre-implementation inventory, 2026-07-21

## Proposed schema changes (migration v7)

The minimum Ticket 5 persistence model is four project-scoped tables:

1. `specification_manifests`: immutable identity and full typed payload. Columns include `id`, `project_id`, monotonic `sequence_number`, `schema_version`, typed `mode`, `policy_version`, `status`, `selected_brief_revision_id`, root/content hashes, actor/origin, `command_id`, `idempotency_key`, `payload`, `created_at`, and optional `exportable_at`. The full payload is stored because Layer 1 and Layer 2 are not yet independently immutable.
2. `specification_manifest_memberships`: immutable, ordered source membership rows keyed by manifest and artifact coordinates. Columns include `manifest_id`, `project_id`, `layer`, `artifact_type`, `logical_artifact_id`, `artifact_revision`, `content_token`, `inclusion_reason`, `ordinal`, and dependency/authority metadata.
3. `specification_manifest_issues`: immutable compiler results keyed by manifest, with stable `issue_code`, validation `stage`, severity, artifact coordinates, message, and structured details.
4. `specification_rendered_artifacts`: immutable render records keyed by manifest and format, containing renderer/schema versions, content hash, local path, command/idempotency identity, and creation time. Rendered bytes are derived only from the stored typed payload.

PostgreSQL and SQLite constraints will enforce project ownership, unique `(project_id, sequence_number)`, unique command/idempotency identities within their intended scope, one deterministic membership coordinate per manifest, known enum values, matching membership/issue project IDs, and append-only protection. The project archive registry will include all four tables. Clone policy is intentionally clean: cloned projects do not inherit compiled manifests or rendered artifact records and must compile against their remapped current artifacts.

## Revision and state-transition model

A compile command snapshots selected sources and creates one immutable manifest record. Manifests are never updated in place. Status transitions are represented by new records or derived render records, not payload mutation.

- `draft`: may contain current kept or non-approved content; all review/freshness exceptions are explicit issues and non-exportable sections are labeled.
- `approved`: selects only production-approved, current, exactly compatible content. Any error makes the manifest non-exportable; canonical rendering requires exportable status.
- `historical`: requires an explicitly selected published brief revision and only compatible historical descendants. If compatible descendants are unavailable, compilation reports/fails; it never substitutes current descendants.
- `diagnostic`: may include stale, cut, rejected, candidate, or superseded records for inspection and is permanently classified noncanonical.

`CompileSpecificationManifest` verifies the expected project state token, selects and validates in one transaction, persists manifest/memberships/issues plus command audit, and commits atomically. Reusing an idempotency key with the same normalized request returns the same manifest; different parameters conflict. `RenderSpecificationManifest` reads one durable manifest, verifies format/mode/exportability rules, writes JSON or Markdown from that payload alone, persists the artifact record and command audit, and is independently idempotent.

## Deterministic selection and matching policy

- Brief: exactly one accessible immutable published revision. Current modes use the brief head's current published revision. Historical mode uses the requested published revision.
- Layer 1: deterministic `(priority nulls last, title casefolded, logical ID)` order. Draft/diagnostic may include kept, prioritized, and explicit human selections; approved includes only canonical kept/prioritized human-accepted pillars. Cut, rejected, merged-away, and superseded pillars are excluded from canonical membership and recorded with reasons.
- Layer 2: include only features owned by an included pillar. Approved mode requires `approved`; draft may include `kept` and `approved`; diagnostic may include every state. Relationships are included only when both endpoints are members. Human-accepted relationship rows are canonical; transient critic recommendations remain provenance/issues.
- Layer 3: at most one active immutable revision per included feature. Approved mode requires approved review state, fresh Ticket 4 state, exact brief/pillar/feature dependency compatibility, and ownership by that project/logical head. Candidates never replace active content. Draft can include a current active non-approved revision with explicit issues. Diagnostic can describe candidates/history separately without promoting them.
- IDs are never fuzzy-matched during compilation. Logical IDs and immutable revision IDs/tokens are copied from canonical records. Content hashes use canonical JSON with sorted keys and stable list ordering.

## Validation pipeline and stable outcomes

The compiler runs fixed stages in order: source integrity, state/approval, structural integrity, semantic consistency, then policy/exportability. Issues use stable codes and `info`, `warning`, or `error` severity. Initial code families are `SOURCE_*`, `STATE_*`, `STRUCTURE_*`, `SEMANTIC_*`, and `POLICY_*`; examples include `SOURCE_BRIEF_MISSING`, `SOURCE_REVISION_INACCESSIBLE`, `STATE_FEATURE_NOT_APPROVED`, `STATE_LAYER3_STALE`, `STRUCTURE_ORPHAN_FEATURE`, `STRUCTURE_RELATIONSHIP_ENDPOINT_MISSING`, `SEMANTIC_LAYER3_SOURCE_MISMATCH`, and `POLICY_NOT_EXPORTABLE`.

The validation summary records gate results, excluded artifacts/reasons, exact/inferred/unknown lineage counts, warnings, and final exportability. Approved manifests are exportable only with no errors and no non-exact required lineage. Diagnostic manifests are never canonical/exportable. Missing provenance is recorded explicitly rather than invented.

## Affected execution paths

- New: typed manifest models, compiler/validator, persistence mixin, renderers, migration v7, compile/render commands, API request/response types, manifest list/detail endpoints, and tests.
- Changed primary path: `POST /api/projects/{project_id}/export` compiles an approved manifest (or selects the idempotent durable result) and renders JSON plus Markdown.
- Preserved compatibility: response still exposes `markdown_path` and `json_path`; additional manifest identity/status/issue fields are additive.
- Reclassified: `/export/layer2` and `/export/layer3` remain available but are diagnostic compatibility exports and will be labeled accordingly in the frontend.
- Preserved separately: diagnostics bundle and project archive remain operational/archival paths, not compiler renderers.
- Lifecycle: full archive/export-import preserves and remaps historical manifests; imported records are marked historical and must be re-rendered because source-machine renderer paths are not trusted; clone starts without manifests; purge cascades/removes manifest records and optionally rendered files.
- Frontend: Export view gains compilation mode, manifest version/time/status, issue summary, durable JSON/Markdown actions, and an advanced diagnostic section. It does not become a general manifest editor.

This inventory is the implementation boundary. It deliberately does not introduce a generic L0-L4 artifact framework, background compiler worker, ContextAssembler integration, prompt-only preservation, or replacement of the Ticket 3 command layer.
